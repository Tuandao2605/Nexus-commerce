# ECOM-DATA-003C — Inventory Domain Model

> Status: FINAL DESIGN — reconciled with DATA-003G remediation

## 1. Scope

DATA-003C thiết kế Inventory Domain cho Nexus Commerce.

Schema V1 gồm 5 bảng:

```text
INVENTORY MODULE
├── warehouses
├── inventory_stocks
├── inventory_reservations
├── inventory_reservation_items
└── stock_movements
```

Mục tiêu chính:

```text
stock = 50

1000 concurrent checkout requests

Expected:
50 success
950 out_of_stock

Invariant:
stock never negative
```

Inventory phải hỗ trợ:

- một Shop có nhiều Warehouse;
- một SKU có thể tồn tại ở nhiều Warehouse;
- InventoryStock không được cross-tenant giữa các Shop;
- reserve stock trước Payment;
- reservation TTL;
- multi-SKU reservation;
- all-or-nothing reservation;
- atomic stock mutation;
- chống overselling;
- deterministic lock ordering;
- idempotent Reserve/Commit/Release;
- phát hiện reuse idempotency key với request khác;
- crash recovery;
- expiration worker;
- immutable stock movement audit;
- future multi-warehouse allocation;
- bảo toàn lịch sử khi Shop/SKU/Warehouse bị archive.

# 8. Reservation Idempotency

## Idempotency Key

```sql
UNIQUE (idempotency_key)
```

Retry cùng command không được tạo reservation thứ hai.

Đây là **internal command identity** do server tạo theo namespace operation,
không phải raw HTTP `Idempotency-Key` do client gửi. Ví dụ canonical key:

```text
inventory:reserve:<checkout_reference_id>:<attempt>
```

Nếu sau này lưu trực tiếp external idempotency key, uniqueness phải bao gồm
actor và operation scope thay vì global trên raw key.

Ví dụ:

```text
ReserveInventory(
    key = "reserve:checkout-123:attempt-1"
)
```

Nếu response bị timeout và caller retry cùng key:

```text
existing reservation được reuse
```

không reserve stock lần hai.

---

# 9. Request Hash

`UNIQUE(idempotency_key)` chưa đủ.

Ví dụ:

```text
Request 1
key = ABC
SKU-A ×2
```

sau đó:

```text
Request 2
key = ABC
SKU-A ×20
```

Không được coi Request 2 là retry hợp lệ.

Invariant:

```text
same key + same request
→ same result
```

```text
same key + different request
→ reject
```

Reservation lưu:

```text
request_hash
```

V1:

```sql
request_hash VARCHAR(64) NOT NULL
```

với SHA-256 hexadecimal.

Constraint:

```sql
CHECK (
    char_length(request_hash) = 64
)
```

Hash được tạo bởi application.

---

# 10. Request Canonicalization

Không hash raw JSON trực tiếp.

Ví dụ hai payload:

```json
{
  "A": 2,
  "B": 1
}
```

và:

```json
{
  "B": 1,
  "A": 2
}
```

có cùng semantic nhưng serialization khác nhau.

Application phải:

```text
1. validate request
2. normalize identifiers
3. aggregate duplicate (shop_id, sku_id)
4. sort (shop_id, sku_id) ascending
5. serialize deterministic representation
6. calculate SHA-256
```

Conceptual canonical representation:

```text
checkout|checkout-reference-id|shop-a|sku-a:2|sku-b:1
```

Hash phản ánh semantic request của caller trước allocation; thay đổi Warehouse
nội bộ không biến một retry hợp lệ thành payload khác.

Sau đó:

```text
SHA256(canonical_request)
→ request_hash
```

---

# 11. Idempotency Handling

Incoming:

```text
key = ABC
hash = HASH-X
```

Nếu key chưa tồn tại:

```text
create reservation
reserve stock
```

Nếu key đã tồn tại:

```text
existing.request_hash == incoming.request_hash ?
```

Nếu giống:

```text
return existing reservation/result
```

Nếu khác:

```text
409 Conflict

IDEMPOTENCY_KEY_REUSED
```

Không mutate existing reservation.

Không reserve thêm stock.

---

## Concurrent Idempotency Race

Không chỉ:

```text
SELECT key

if not exists:
    INSERT
```

vì hai request concurrent có thể đều đọc `not found`.

Database:

```sql
UNIQUE(idempotency_key)
```

là final protection.

Nếu INSERT gặp unique violation:

```text
load existing reservation
compare request_hash
```

Sau đó:

```text
same hash
→ return existing

different hash
→ conflict
```

# 14. Logical Status vs Effective Status

`status = active` chưa đủ để reservation còn hợp lệ.

Definition:

```text
Effectively Active
=
status = 'active'
AND expires_at > now()
```

Có thể tồn tại transient state:

```text
status = active
expires_at <= now()
```

vì worker chưa cleanup.

Nhưng về business:

```text
reservation đã hết hạn
```

Trong khoảng worker chưa cleanup, quantity hết hạn có thể vẫn nằm trong
`reserved_quantity` và làm availability thấp hơn thực tế. Đây là conservative
blocking (không gây oversell), nhưng worker phải chạy liên tục với SLO rõ ràng;
reserve path nên opportunistically cleanup các hold hết hạn trên stock rows đang
được xét để giảm false out-of-stock.

---

# 15. `expires_at` Is the Business Deadline

```text
expires_at
=
business validity deadline
```

```text
expiration worker
=
asynchronous cleanup mechanism
```

Không định nghĩa:

```text
worker chưa chạy
→ reservation vẫn hợp lệ
```

Ví dụ:

```text
expires_at = 10:15:00
now        = 10:15:03
status     = active
```

Business interpretation:

```text
expired
```

---

# 16. Commit Preconditions

Commit chỉ hợp lệ khi:

```text
status = active
AND
expires_at > now()
```

Conceptual:

```sql
SELECT *
FROM inventory_reservations
WHERE id = $1
  AND status = 'active'
  AND expires_at > now()
FOR UPDATE;
```

Nếu:

```text
expires_at <= now()
```

commit bị reject dù status trong DB vẫn đang là ACTIVE.

Expected application error:

```text
RESERVATION_EXPIRED
```

---

# 17. Commit After Expiry

Ví dụ:

```text
expires_at = 10:15:00

10:15:03:
status = active

worker chưa chạy
```

Payment callback gọi:

```text
CommitReservation()
```

Result:

```text
reservation_expired
```

Không:

```text
on_hand -= quantity
```

Không tạo:

```text
SALE movement
```

Expiration worker sẽ cleanup sau.

# 28. Atomic Reservation

Critical operation:

```sql
UPDATE inventory_stocks
SET
    reserved_quantity = reserved_quantity + $2,
    updated_at = now()
WHERE id = $1
  AND on_hand_quantity - reserved_quantity >= $2;
```

Result:

```text
rows affected = 1
→ success

rows affected = 0
→ insufficient stock
```

Check và mutation xảy ra trong một DB operation.

Không làm:

```sql
SELECT on_hand_quantity, reserved_quantity;
```

rồi trong Go:

```text
if available >= qty:
    UPDATE
```

vì có race condition giữa concurrent processes.

# 29. Last Item Concurrency

Initial:

```text
on_hand = 1
reserved = 0
```

Checkout A và B đồng thời reserve 1.

PostgreSQL serialize row updates.

Một request thành công:

```text
reserved = 1
```

Request còn lại evaluate:

```text
on_hand - reserved = 0
```

→ fail.

Expected:

```text
1 success
1 out_of_stock
```

Không bao giờ:

```text
reserved = 2
```

# 30. Multi-SKU Reservation

Checkout:

```text
SKU-A ×2
SKU-B ×1
SKU-C ×5
```

Policy:

```text
ALL OR NOTHING
```

Conceptual:

```text
BEGIN

create reservation

reserve A
insert item A

reserve B
insert item B

reserve C
insert item C

COMMIT
```

Nếu C fail:

```text
ROLLBACK
```

Sau rollback:

```text
A unchanged
B unchanged
C unchanged

reservation not created
items not created
```

# 31. Rollback vs Compensation

Trong cùng PostgreSQL transaction:

```text
failure
→ ROLLBACK
```

Không cần manual compensation.

Phân biệt:

```text
inside same DB transaction
→ rollback
```

```text
across already-committed services/modules
→ compensation
```

```text
Tx2:
```

# 33. Row Locking Strategy

Single stock reservation không cần `SELECT FOR UPDATE` trước conditional UPDATE.

Conditional UPDATE tự lock row.

V1 multi-item strategy:

```text

conditional UPDATE A
conditional UPDATE B
conditional UPDATE C
```

trong cùng transaction.

Nếu logic allocation phức tạp sau này có thể dùng:

```sql
SELECT ... FOR UPDATE
```

theo deterministic ordering.

# 34. Reservation Transaction

Conceptual:

```sql
BEGIN;

INSERT INTO inventory_reservations (...);

UPDATE inventory_stocks
SET reserved_quantity = reserved_quantity + 2
WHERE id = :stock_a
  AND on_hand_quantity - reserved_quantity >= 2;

-- rows affected must equal 1

  AND on_hand_quantity - reserved_quantity >= 1;
```

# 35. Commit Reservation

Commit chỉ hợp lệ khi:

```text
status = active
AND expires_at > now()
```

Conceptual transaction:

```text
BEGIN

lock reservation

validate:
    status = active
    expires_at > now()

load reservation items
ordered by inventory_stock_id ASC

for each item:

    on_hand -= quantity
    reserved -= quantity

    INSERT SALE movement

update reservation:
    status = committed
    committed_at = now()

COMMIT
```

Current stock mutation và movement insert phải cùng transaction.

# 36. Commit Idempotency

Payment provider có thể gửi callback nhiều lần.

Nếu reservation đã:

```text
COMMITTED
```

gọi commit lần hai không được:

```text
on_hand -= qty
```

lần nữa.

Terminal side effects phải execute exactly once từ góc nhìn business transaction.

# 37. Release Reservation

Manual/business release:

```text
ACTIVE → RELEASED
```

Transaction:

```text
BEGIN

lock reservation

validate effective state

for each item:
    reserved -= quantity

update reservation:
    status = released
    released_at = now()

COMMIT
```

Không giảm `on_hand`.

Không tạo stock movement.

## Release After Deadline

Nếu:

```text
expires_at <= now()
```

V1 semantic:

```text
EXPIRED
```

không phải RELEASED.

`RELEASED` dành cho chủ động hủy trước deadline.

`EXPIRED` dành cho timeout.

# 38. Release Idempotency

Nếu đã:

```text
RELEASED
```

gọi release lần hai không được giảm:

```text

```

thêm lần nữa.

# 39. Expiration Worker

Reservation TTL target V1:

```text
15 minutes
```

Worker:

```sql
SELECT id
FROM inventory_reservations
WHERE status = 'active'
  AND expires_at <= now()
ORDER BY expires_at
FOR UPDATE SKIP LOCKED
LIMIT $1;
```

Sau đó trong transaction:

```text
reserved -= reservation item quantities

status = expired
expired_at = now()
```

`FOR UPDATE SKIP LOCKED` cho phép nhiều worker chạy parallel mà không cùng xử lý một reservation.

# 40. Process Crash Recovery

Nếu process crash sau reservation commit vào DB:

```text
reservation remains ACTIVE
reservation items remain
reserved quantities remain
expires_at remains
```

Sau restart:

```text
expiration worker
→ finds expired reservation
→ releases stock
```

Không phụ thuộc:

```text
Go in-memory timers
```

# 41. Commit vs Expiration Race

Có:

```text
Payment callback
→ CommitReservation
```

và:

```text
Expiration Worker
→ ExpireReservation
```

đồng thời.

Cả hai serialize trên reservation row.

### Commit wins before deadline

```text
status = active
expires_at > now()

ACTIVE → COMMITTED
```

Worker sau đó no-op.

### Worker wins after deadline

```text
ACTIVE → EXPIRED
```

Commit sau đó reject.

### Commit arrives after deadline, worker chưa chạy

Commit vẫn phải reject vì:

```text
expires_at <= now()
```

Worker timing không được kéo dài TTL.

```text

14. Reservation idempotency_key unique.

16. Same key + different hash bị reject ở application layer.

20. COMMITTED có committed_at.
```
