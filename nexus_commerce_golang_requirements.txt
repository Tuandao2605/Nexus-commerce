NEXUS COMMERCE
Production-Grade Multi-Vendor E-Commerce Platform

Backend: Golang
Architecture: Modular Monolith -> Event-Driven Microservices
Database: PostgreSQL
Mục tiêu: Backend / Distributed Systems / Security / DevOps / Production Engineering

1. TỔNG QUAN
============

Xây dựng một nền tảng thương mại điện tử multi-vendor tương tự phiên bản thu nhỏ của Shopee/Lazada.

Hệ thống không chỉ dừng ở CRUD mà phải giải quyết những vấn đề thực tế:
- Authentication & Authorization
- Multi-vendor architecture
- Product/SKU modeling
- Inventory concurrency
- Distributed transactions
- Payment reliability
- Idempotency
- Event-driven architecture
- Cache consistency
- Search
- Security
- Observability
- Resilience
- Load testing
- CI/CD
- Container orchestration

Mục tiêu cuối cùng là xây dựng một backend có thể giải thích được:
Điều gì xảy ra nếu request bị gửi lại, hai người mua sản phẩm cuối cùng cùng lúc, Redis chết, payment timeout, webhook đến hai lần, broker ngừng hoạt động hoặc một service crash giữa transaction?

11. INVENTORY CONCURRENCY
=========================

Giả sử stock = 50
Có 1000 concurrent checkout requests

Expected:
- 50 success
- 950 out-of-stock
- stock >= 0

Không được overselling.

Phải nghiên cứu và lựa chọn giữa:
- atomic SQL update
- optimistic locking
- pessimistic locking
- PostgreSQL row locking

Phải hiểu goroutine synchronization không thay thế được database concurrency control khi chạy nhiều application instance.

17. PAYMENT IDEMPOTENCY
=======================

Nếu payment provider gửi nhiều PAYMENT_SUCCESS trùng lặp,
Order chỉ được PAID một lần.

Không được:
- double charge
- double inventory commit
- double notification
- duplicate accounting operation

18. API IDEMPOTENCY
===================

Critical write APIs phải hỗ trợ:
Idempotency-Key

Ví dụ:
POST /checkout
Idempotency-Key: 550e8400...

Client gửi request 5 lần vì timeout.

Expected:
- 1 checkout
- 1 order
- 1 payment

Thiết kế storage:
- IdempotencyKey
- requestHash
- status
- response
- expiresAt

Reuse cùng key nhưng request body khác phải bị reject.

20. TRANSACTIONAL OUTBOX
========================

Không được:
UPDATE database
broker.Publish()

và giả định cả hai luôn thành công.

Phải implement Transactional Outbox Pattern:
BEGIN
UPDATE orders ...
INSERT INTO outbox_events ...
COMMIT

Sau đó:
Outbox Worker -> Message Broker -> Consumers

Nếu broker chết, event vẫn tồn tại trong database để retry.

21. RELIABLE CONSUMER
=====================

- network failure
- out-of-order event

Consumer phải idempotent.

Có thể implement Inbox Pattern hoặc cơ chế tương đương.

Phải chứng minh At-least-once delivery không làm business operation chạy nhiều lần.

50. DEFINITION OF DONE
======================

Inventory:
stock >= 0 trong mọi concurrency test.

Payment:
one successful payment -> one business payment effect

Duplicate webhook không gây double processing.

Order:
State transition luôn hợp lệ.

Idempotency:
same request + same Idempotency-Key -> same business result

Events:
Duplicate delivery không tạo duplicate business operation.

Failure:
Service crash không làm mất business-critical operation đã commit.

Security:
User/Seller không truy cập hoặc chỉnh sửa tài nguyên không thuộc quyền của mình.

Observability:
Có thể xác định nguyên nhân của:
- slow request
- failed checkout
- failed payment
- consumer failure
- database bottleneck

52. PHƯƠNG PHÁP THỰC HIỆN
=========================

Không implement toàn bộ specification cùng lúc.

Mỗi Phase được chia thành engineering tickets.

Ví dụ:
ECOM-INV-07
Atomic Inventory Reservation

Requirement:
Stock = 50
500 concurrent reservation requests

Acceptance Criteria:
- Exactly <= 50 successful reservations
- Inventory never becomes negative
- Operation is transaction-safe
- Multiple API instances remain safe
- Integration test exists
- Concurrency test exists

Developer phải tự:
Research -> Design -> Implement -> Test -> Benchmark -> Code Review

Không chuyển sang ticket tiếp theo chỉ vì code chạy được.

Mỗi ticket phải được review về:
- Correctness
- Security
- Concurrency
- Transaction boundary
- Failure handling
- Performance
- Maintainability
- Testability
- Observability

Mục tiêu của đồ án không chỉ là hoàn thành sản phẩm.
Mục tiêu là học cách thiết kế, xây dựng, phá thử, quan sát, sửa và vận hành một backend lớn bằng Go như một hệ thống production thực tế.
