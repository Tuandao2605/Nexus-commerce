# ECOM-DB-004E — Cart Schema

Status: DONE

## Source Design

- DATA-003D — Cart
- DATA-003G — Full ERD corrections

## Goal

Implement PostgreSQL schema for:

- carts
- cart_items

## Important Invariants

- One User has at most one active Cart
- A User may retain many terminal Carts
- Cart is global and intentionally has no shop_id
- CartItem.shop_id must match SKU.shop_id
- One SKU appears once inside one Cart
- CartItem quantity is between 1 and 99
- Cart status must match its terminal timestamp
- Cart stores purchase intent, not price or inventory reservation
- SKU inactive/archive does not remove CartItem
- Partial checkout removes only selected items and terminalizes Cart only when empty
- CartItem mutation and lifecycle transition must serialize on the Cart row in the future repository/service transaction

## Implementation

Migrations:

- `000005_cart.up.sql` creates Cart lifecycle, CartItem tenant constraints and indexes
- `000005_cart.down.sql` rolls back Cart tables in dependency-safe order

Integration tests:

- `cart_migration_test.go` proves Cart schema, lifecycle, transaction and concurrency invariants on PostgreSQL
- `migration_test_helpers_test.go` supplies shared pool, transaction, UUIDv7 and SQLSTATE helpers
- `seller_catalog_migration_test.go` supplies User, Shop and SKU fixtures required by Cart tests

Important DB constraints:

- partial `UNIQUE(user_id)` while Cart status is active
- FK Cart → User with `ON DELETE RESTRICT`
- composite FK CartItem → SKU/Shop with `ON DELETE RESTRICT`
- `UNIQUE(cart_id, sku_id)` on CartItem
- CHECK quantity between 1 and 99
- CHECK Cart status and terminal timestamp compatibility
- CHECK timestamp chronology
- no Cart-level shop, price, total, currency or stock fields
- no CartItem price, stock or reservation fields

## Decisions

- UUIDv7 generated by Go
- Cart is one global multi-Shop purchase-intent container
- CartItem references the final sellable SKU and repeats shop_id only for tenant-safe FK/grouping
- quantity uses BIGINT with V1 maximum 99
- no PostgreSQL ENUM
- no price snapshot/cache in Cart V1
- no inventory fields or reservation side effect in Cart
- a global Cart may retain mixed-currency items; one V1 checkout selection must use one currency
- partial checkout is a transaction/service rule, demonstrated here with PostgreSQL SQL but implemented later by CheckoutService
- terminal Cart immutability is a transaction/service rule; every future CartItem mutation must lock and validate the active Cart row first
- concurrent add uses atomic PostgreSQL UPSERT with the upper-bound predicate
- PostgreSQL access prioritizes pgx + sqlc; no GORM
- sqlc queries, Cart repository/service, HTTP handlers and Checkout orchestration remain outside this schema ticket
