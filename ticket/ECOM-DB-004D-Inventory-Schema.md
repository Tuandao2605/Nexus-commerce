# ECOM-DB-004D — Inventory Schema

Status: DONE

## Source Design

- DATA-003C — Inventory
- DATA-003G — Full ERD corrections

## Goal

Implement PostgreSQL schema for:

- warehouses
- inventory_stocks
- inventory_reservations
- inventory_reservation_items
- stock_movements

## Important Invariants

- Warehouse belongs to exactly one Shop
- Warehouse.shop_id must match InventoryStock.shop_id
- SKU.shop_id must match InventoryStock.shop_id
- One current stock row per Warehouse and SKU
- on_hand_quantity >= reserved_quantity >= 0
- available quantity is derived and must not be persisted
- Reservation idempotency key is unique
- Inventory checkout reference always uses checkout_reference_id
- Reservation expiry is a business deadline, independent of worker timing
- Reservation items have positive quantity and are unique per Reservation/Stock
- Physical stock movements have a non-zero delta with the correct direction
- Inventory history must not cascade-delete

## Implementation

Migrations:

- `000004_inventory.up.sql` creates Inventory state, reservation and ledger tables with constraints/indexes
- `000004_inventory.down.sql` rolls back Inventory tables in dependency-safe order

Integration tests:

- `inventory_migration_test.go` proves Inventory schema, transaction and concurrency invariants on PostgreSQL
- `migration_test_helpers_test.go` supplies shared pool, transaction, UUIDv7 and SQLSTATE helpers
- `seller_catalog_migration_test.go` supplies tenant-safe Shop/SKU fixtures required by Inventory tests

Important DB constraints:

- `UNIQUE(shop_id, code)` and `UNIQUE(id, shop_id)` on Warehouse
- composite FK InventoryStock → Warehouse/Shop
- composite FK InventoryStock → SKU/Shop
- `UNIQUE(warehouse_id, sku_id)` on InventoryStock
- CHECK on non-negative on-hand/reserved and reserved <= on-hand
- `UNIQUE(idempotency_key)` on InventoryReservation
- CHECK `reference_type = 'checkout'`
- CHECK reservation status timestamps and expiry chronology
- `UNIQUE(reservation_id, inventory_stock_id)` on ReservationItem
- CHECK movement type, non-zero delta and delta direction
- `ON DELETE RESTRICT` on every Inventory FK

## Decisions

- UUIDv7 generated by Go
- quantities stored as BIGINT
- current state belongs to inventory_stocks
- available quantity is calculated as on_hand_quantity - reserved_quantity
- stock_movements is the immutable audit ledger
- Reserve, release and expire do not create physical movements
- Commit creates a SALE movement in the same future service transaction
- V1 reservation reference is checkout_reference_id
- V1 reservation TTL target is 15 minutes
- UNIQUE idempotency key is the race guard; application compares request_hash on retry
- multi-stock mutations use one PostgreSQL transaction and deterministic stock ID ordering
- PostgreSQL access prioritizes pgx + sqlc; no GORM
- sqlc queries, Inventory service and expiration worker remain outside this schema ticket
